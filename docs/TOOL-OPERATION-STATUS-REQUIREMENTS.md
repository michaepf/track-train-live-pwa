# Tool Operation Status and Recovery Requirements

## Status

Draft for implementation planning. This document defines product and architectural requirements; it does not prescribe a complete implementation.

## Problem

When the trainer is responding, the chat currently shows animated dots or streamed text. Users cannot reliably tell when the app is validating a tool call, changing local data, correcting an invalid call, or recovering from a failure.

Some error recovery already exists:

- Invalid tool calls are returned to the model and retried automatically, up to a limit.
- Tool execution failures are recorded and displayed, but the model does not get an immediate opportunity to correct them.
- Fake tool narration is detected in some conversation modes, but recovery requires the user to send a pre-filled corrective message.
- Failures while accepting profiles, goals, training plans, and workouts are handled inconsistently.

This is manageable for a developer who can infer what happened and prompt the trainer again. A normal user needs an explicit, trustworthy account of what the app attempted, what actually changed, and what to do next.

## Goals

1. Show concise, literal activity text based on actual client events.
2. Never imply that data changed until the client has verified the operation's outcome.
3. Give users a clear and actionable explanation when an operation fails.
4. Preserve and generalize the existing bounded model self-correction behavior.
5. Apply consistent operation handling to automatic tools and user-approved proposals.
6. Extract the tool-operation lifecycle from `Chat.tsx` without expanding this work into a full conversation-engine refactor.
7. Keep model-facing diagnostics precise while keeping user-facing language non-technical.

## Non-goals

- Exposing chain-of-thought, raw tool arguments, hidden prompts, or developer diagnostics.
- Replacing the existing proposal-card interaction model.
- A full extraction of streaming or conversation persistence from `Chat.tsx`.
- Server synchronization, telemetry, background jobs, or cross-device recovery.
- Unbounded autonomous retries.
- Parallel or multiple tool calls in a single model turn unless separately scoped.
- Changing workout data rules or weakening completed-workout immutability.

## Experience principles

### Status must reflect verified client state

Status text must be derived from the tool call and its client-side lifecycle, not generated by the model. The UI must not say that an operation is running until an actual tool call has been received.

Examples:

- `Updating your workout...`
- `Workout updated.`
- `Couldn't update the workout.`

The app must not display `Workout updated` because the assistant claimed it was updated. A verified executor or persistence result is authoritative.

### Failures must answer three questions

A terminal failure shown to the user must communicate:

1. What was attempted?
2. What changed, if anything?
3. What can the user do next?

User-facing text must not expose raw tool names, JSON, record IDs, entry indexes, stack traces, or hidden retry instructions.

### Approval is not execution

Proposal states must remain distinct from saved states. For example, `Ready for your review` must not be presented as `Workouts saved`.

### Visibility should match significance

- Very fast operations should be debounced to avoid visual flicker.
- Routine read-only success statuses may disappear after a short confirmation.
- Meaningful mutations should receive a visible success confirmation.
- `no_change`, partial success, and failures must remain visible long enough to understand.
- Terminal failures must remain in the conversation until superseded or dismissed through an intentional interaction.

## Operation lifecycle

The shared lifecycle must represent at least:

- `running`: a valid operation is being processed.
- `correcting`: the model is correcting an invalid or correctable call.
- `awaiting_approval`: a valid proposal requires user action and has not changed data.
- `succeeded`: the requested state change was verified.
- `no_change`: the operation completed but did not alter data.
- `partially_succeeded`: part of a multi-record operation succeeded and part did not.
- `failed`: the operation did not complete and cannot continue automatically.

An operation chain must have its own identity and retry count. Retry state must not leak into a later, unrelated tool call or conversation.

## Failure classification and recovery

Failures must be classified so the recovery action is appropriate rather than uniformly offering `Retry`.

### Model-correctable failure

Examples include malformed arguments, stale entry references, or an unknown exercise ID that the model can replace.

- Return precise structured context to the model.
- Allow a bounded automatic correction attempt.
- Preserve the current maximum of two automatic validation corrections unless testing supports changing it.
- After exhaustion, show a persistent friendly failure and enable user input.

### Permanent rule conflict

Examples include attempting to edit a completed workout or a set that already has difficulty logged.

- Do not blindly retry.
- Explain the rule in plain language.
- Offer an alternative only when one is valid, such as planning a new workout.

### Transient failure

Examples include an IndexedDB transaction failure or interrupted API stream.

- Offer retry when the operation is known not to have committed, or when retry is idempotent.
- Do not automatically retry a mutation whose commit status is unknown.
- Preserve the user's input and keep the conversation usable.

### Partial mutation

Examples include saving two proposed workouts before the third save fails.

- Report exactly what was saved and what was not.
- Do not claim total success or total failure.
- A retry must not duplicate records already saved.
- The recovery action must operate only on the unsaved portion or re-check current state before writing.

### Unknown failure

- State that the requested change could not be verified.
- Do not claim data is unchanged if commit status is unknown.
- Provide a safe next action, such as reloading current state before retrying.

## Functional requirements

1. Display a compact activity row while a tool operation is running or correcting.
2. Use a friendly activity description mapped from the actual operation and, where safe, its target.
3. Show verified mutation success separately from the assistant's conversational response.
4. Show `no_change` when an operation was valid but had no effect, including duplicate exercise additions and edits that preserve existing values.
5. Preserve existing automatic correction for malformed or invalid tool calls.
6. Allow execution failures to trigger bounded model self-correction only when classified as model-correctable.
7. Never blindly retry mutations.
8. Return model-facing tool results in the valid assistant/tool message order required by the API.
9. Keep model-facing tool results hidden from the normal chat transcript.
10. Keep chat input enabled after a terminal failure unless a valid approval card is awaiting action.
11. Apply consistent busy, success, and failure behavior when accepting:
    - profile proposals;
    - goal proposals;
    - training-plan proposals;
    - workout proposals.
12. Distinguish stream/API errors from local tool execution errors while presenting both in plain language.
13. Detect and ignore stale async completion after a conversation reset, component unmount, or operation replacement.
14. Preserve current proposal acceptance and rejection behavior unless a change is necessary for correct status reporting.

## Structured outcomes

Tool execution and proposal persistence must return or be converted into a strict discriminated outcome rather than relying on human-readable strings or uncategorized thrown errors.

The outcome must provide enough structured information to determine:

- success, no-change, partial-success, or failure status;
- whether any local state changed;
- operation and stable failure code;
- retry and recovery classification;
- model-facing details;
- safe user-facing description data;
- affected and unaffected item counts for batch operations.

Unexpected exceptions may still be caught at the runtime boundary, but they must be converted into an `unknown` structured failure before reaching the UI.

## Architectural requirements

### Focused extraction

Extract a focused tool-operation runtime rather than the full conversation engine.

The intended responsibility split is:

- `Chat.tsx`: conversation composition, screen-level state, and presentation assembly.
- Tool-call resolution: schema validation and categorization into approval, execution, or validation failure.
- Tool executors: device-local reads and writes that return structured outcomes.
- Tool-operation runtime: lifecycle state, execution coordination, failure classification, retry policy, and requests for a follow-up model turn.
- Activity component: accessible rendering of running, success, no-change, partial-success, and failure states.

The runtime must expose explicit outcomes to `Chat.tsx`; it must not depend on parsing assistant prose.

### Scope boundaries

- Existing data-model rules remain non-negotiable.
- `saveWorkout()` must continue preserving unknown fields.
- Completed workouts remain immutable.
- The `difficulty` enum remains the only set-completion signal.
- No `any`, suppressed TypeScript errors, or untyped error payloads may be introduced.

### File-size objective

The extraction must materially reduce the tool-lifecycle responsibility and line count in `Chat.tsx`. Moving code into a pass-through helper without clarifying ownership does not satisfy this requirement.

## Accessibility requirements

- Status changes must be understandable without relying on animation or color.
- Use restrained live-region announcements so rapid transitions do not produce excessive screen-reader output.
- Do not repeatedly announce decorative progress animation.
- Respect reduced-motion preferences.
- Recovery controls must have descriptive accessible labels.

## Verification strategy

Verification must use a hybrid approach. The OpenRouter PKCE flow and live model behavior make a fully mocked browser flow both expensive to maintain and less representative than a real authenticated session.

### Deterministic automated coverage

- The operation runtime must accept an executor boundary that tests can replace without OpenRouter authentication.
- Unit tests must inject structured `succeeded`, `no_change`, `partially_succeeded`, and `failed` outcomes directly.
- Retry classification, retry exhaustion, tool-message ordering, stale-operation protection, and user-facing status selection must be testable without a live model.
- IndexedDB behavior should use the existing fake IndexedDB test environment where persistence behavior itself is under test.
- Tests must not depend on persuading a model to emit malformed arguments or a particular tool call.

### Authenticated manual coverage

Live verification will be performed periodically by the user against the local Vite app exposed privately through Tailscale Serve over HTTPS. The HTTPS origin is required for the Web Crypto API used by OpenRouter PKCE authentication.

The manual checklist must remain short and scenario-based:

1. Ask for and accept a workout proposal.
2. Ask the trainer to edit a planned workout.
3. Trigger a safe no-change operation.
4. Interrupt a response and verify that recovery is understandable.
5. Confirm that running, success, and failure language is readable on mobile.

Live testing is responsible for confirming that real OpenRouter tool calls enter the client lifecycle correctly. Difficult-to-induce failures, including partial writes and stale references, remain the responsibility of deterministic automated tests.

The local service must not be exposed publicly. Tailscale Serve, not Funnel, is the intended remote testing path.

## Required edge cases

The design and tests must cover:

- Invalid JSON or schema arguments that fail twice.
- A model narrating a tool call without emitting one.
- A workout missing or changing after the model received its context.
- A completed workout edit attempt.
- A set gaining `difficulty` before an edit executes.
- Stale entry or set references.
- Adding an exercise that already exists.
- An edit that produces zero effective changes.
- Future-workout deletion containing both completed skips and genuine deletion failures.
- A multi-workout acceptance that fails after one or more successful saves.
- A domain mutation succeeding while conversation persistence fails.
- A reset, unmount, or abort during an operation.
- A follow-up tool call after a successful edit, delete, or swap.
- Very fast local operations that would otherwise cause status flicker.

## Acceptance criteria

1. A successful mutation shows an accurate running phrase and a completion state derived from verified executor output.
2. A failed completed-workout edit leaves workout data unchanged, explains the permanent conflict in plain language, and does not offer blind retry.
3. Correctable validation failures retain the existing maximum-two automatic correction behavior.
4. After correction attempts are exhausted, a persistent user-facing failure appears and chat input is enabled.
5. A model-correctable execution failure can initiate a bounded follow-up turn without requiring the user to diagnose it.
6. Profile, goals, training-plan, and workout acceptance failures are all caught and surfaced consistently.
7. Partial workout saves report accurate saved and unsaved counts and cannot be retried in a way that duplicates saved workouts.
8. Duplicate exercise additions and edits with no effective changes produce `no_change`, not misleading success or failure.
9. Future-workout deletion distinguishes completed-workout skips from genuine deletion failures.
10. User-facing operation states contain no raw tool names, IDs, indexes, JSON, stack traces, or hidden prompts.
11. Existing valid tool-call protocol behavior continues to work.
12. New unit tests cover outcome classification, recovery policy, retry exhaustion, and partial success.
13. The full test suite and production build pass in strict TypeScript mode.
14. `Chat.tsx` is materially smaller and no longer owns tool execution and recovery policy directly.

## Implementation sequencing recommendation

1. Add characterization tests for current validation retry and tool-message ordering.
2. Introduce structured outcome and failure-classification types.
3. Convert executors and proposal persistence to structured outcomes.
4. Extract the focused operation runtime while preserving behavior.
5. Add the activity and recovery UI.
6. Add edge-case tests, accessibility checks, and end-to-end verification.

Each step should leave the app buildable and testable. Structural extraction and visible behavior should be separable commits where practical.

## Open product decisions

The following can be settled during implementation planning without changing the core requirements:

- How long successful mutation confirmations remain visible.
- Whether completed activity collapses into a compact persistent summary.
- The exact phrase set and tone for each operation.
- Whether a terminal error can be dismissed manually or only superseded by later activity.
- Whether transient stream failures use `Retry`, `Resend`, or both depending on available state.
